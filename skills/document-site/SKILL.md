**You own this task. Document the repo from evidence, ask the architect only what evidence cannot answer, and land one docs-only PR.**

Read `.claude/site.md` first. If it does not exist, stop and say so; the install step creates it with Identity filled.

## Non-negotiables

- Interview the repo, not the architect. The architect is step 7 and only gets questions the code and history could not answer.
- Every claim in a profile field, a Gotchas bullet, or a note carries a tier: Direct, Supported, Inferred, or Unknown. An Unknown names what was searched and ends with "preserve as-is."
- The feature map is the only doc tree. No architecture pages, no decisions folder, no gotchas folder, no runbooks. A cross-cutting fact becomes a note only when an agent would reliably get it wrong without it.
- Never edit product code in this skill. Comment harvesting (step 5) is a separate run the architect opts into per repo.
- Never edit a tool-owned path: serialized content, migrations, generated code.
- The read-first set, `CLAUDE.md` plus the profile, stays under 16 KB. Anything situational goes to a note with a trigger line or a feature file.
- One topic per file, under fifty lines. Split rather than grow.
- `docs/index.md` is generated by the hook. Never write it by hand.

## Steps

Copy these into your todo list verbatim. A skipped step stays visible as `skip: <reason>`.

1. **Interview the repo.** Spawn read-only explorer subagents with `references/explorer-prompt.md`, one per top-level module (on a Helix solution: Foundation, Feature, Project) and one per obvious subsystem (routing and rendering, data access, search, forms, caching, configuration, background jobs, the front end if it is separate). Each returns the fixed report shape. Read the tool-owned paths to list what they define. Read the configuration roots for override order. Read the build: solution or workspace file, project references, package feeds, runtime versions. Attempt the build with the command you infer and record pass, fail, or could not run; "has a build" and "can run tests" are different facts.
2. **Draft the site profile.** Fill `.claude/site.md` from `references/profile-fields.md`. Discover, do not ask: the stack and runtime versions, the top-level modules and whether they follow Helix, the tool-owned paths and the tool that writes them, the configuration roots, the gating files. Fill Verification with the commands you ran. Mark the rest unknown. Write the entries you are least sure of as proposal cards in `docs/open-questions.md` under "Confirm," one line each with your proposed value, so the architect approves or edits rather than answers from scratch.
3. **Draft the feature map.** From routes, views, and entry points. One file per user-facing area using `docs/_templates/feature-page.md`. "Driving it" is real where the app runs and a static trace where it does not, with the evidence ceiling stated. "Files" lists real paths; it is the contract the PR docs check reads. Each explorer's "Non-obvious things" that belong to one area land in that area's Gotchas with their tier. Write `docs/features/README.md` with the preconditions and the sweep order.
4. **Write and prove the verify skill, where the app runs.** When the evidence ceiling is `app runs`, write `.claude/skills/verify/SKILL.md` from `references/verify-skill.md` and run every section once against the endpoints named in the profile. Record each section's result in the PR body; a section that could not run says why. Otherwise: `skip: no runnable environment`.
5. **Harvest comments.** `skip: separate opt-in run` unless the architect invoked this skill with `with-comments`. When invoked that way, follow `references/comment-harvest.md` and put the product-code changes in their own commit.
6. **Harvest history, then apply the bar.** Run the `why` investigation from `references/why-prompt.md` over the targets the explorers flagged: defensive code, odd decisions, reverted fixes, fences. For each result ask: would an agent reliably get this wrong without it? Yes and it belongs to one area: a Gotchas bullet there. Yes and it cuts across areas: one note from `docs/_templates/note.md` with a trigger line. No: nothing, the history has it. Gaps are recorded as Unknown with "preserve as-is," and only where the fence is one an agent might otherwise remove.
7. **Interview the architect, last.** Collect every open question from steps 1 to 6. Group by area. Write them to `docs/open-questions.md` in the format in `references/interview-format.md`: four to six per batch, each with concrete options and your bet, never a blank "tell me about the site." Do not wait for answers; `/docs-answer` writes them back later.
8. **Validate like a cold agent.** Run `/validate-docs` on the first feature in sweep order. Fix anything that sent the cold agent the wrong way before continuing.
9. **Encode.** Anything the explorers found enforced by convention alone, or the history shows was broken twice, gets a row in the rule table in `CLAUDE.md` with its enforcer, or "none yet." First candidates: module layering as a project-reference check (on Helix: Foundation never references Feature, Feature never references Feature), and an edit under a tool-owned path.
10. **Write the root files.** `CLAUDE.md` from its template, under forty lines, with the must-read pointers to the feature files and the one note that bites most, the commands from the profile's Verification section, and the rule table. `AGENTS.md` from its template, a pointer to `CLAUDE.md`.
11. **Open the PR.** Draft. One PR confined to `docs/`, `.claude/`, `CLAUDE.md`, and `AGENTS.md`. Title `docs: document site`. Body: what was found, the evidence ceiling, the verify skill's results if one was written, the count of open questions, the count of rules without an enforcer, the validate-docs score.

## Reply

What was documented, the evidence ceiling and why, the number of feature files and notes, the number of open questions by group, the number of Unknowns recorded, the rules without an enforcer, the validate-docs score, and the PR link.
